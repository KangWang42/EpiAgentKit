# 数据型网页应用的读取、刷新与渲染

适用于登录后显示服务器数据、会自动或按变更刷新的网页应用（管理台、监测面板、邮件或消息列表等），以及用户反映读取、切换、刷新、滚动卡顿的情况。公开页首次加载的目标仍按 [quality-gates.md](quality-gates.md#性能)。

## 1. 先测量时间花在哪

改动前在同一条件下记录一组基线，按结果决定改哪一层，不凭印象重写框架：

- **网络**：分别测新建连接与复用连接的单次请求（如 `curl -w` 的 `time_connect`、`time_appconnect`、`time_starttransfer`，同一进程多个 URL 观察复用）。两者差距大时优先保证连接复用和减少请求次数。
- **服务端**：在服务器本机回环测同一接口的冷、热耗时，与公网耗时对比，分出网络与处理时间。
- **负载**：记录每个接口的原始与压缩体积，并按字段统计体积占比；只记录大小，不保存响应正文。
- **客户端**：用真实浏览器记录 DOMContentLoaded、长任务和脚本执行；手机体验以 CPU 降速 4 倍作近似并注明。
- **刷新频率**：查清什么事件触发重新读取和整页重画，以及实际多久触发一次。

每项改动完成后用同一方法复测，对比时注明冷热缓存和数据量变化；方向性观察不写成性能承诺。

## 2. 读取：只传变化

1. 读接口返回内容哈希 `ETag`，客户端带 `If-None-Match`，未变化时回 304；鉴权在命中缓存前执行，`Vary` 包含会话凭据。
2. 客户端先显示上次保存的数据，再向服务器确认（stale-while-revalidate）；答复与已显示内容相同时不解析、不重画，只更新“更新时间”。保存的数据随登出清除，只存当前账号可见内容。
3. 列表视图与详情分开：列表只带卡片实际用到的字段，曲线、正文等按需读取。确需在列表里带时间序列时，可用列式紧凑格式（键列表加行数组），并保留旧格式作默认以兼容旧客户端。
4. 预取下一步最可能打开的少量内容（如列表顶部若干封邮件的已保存正文），使用不产生副作用的批量读接口：不标已读、不触发外部抓取，并限制条数。

## 3. 刷新：区分“数据变了”和“遥测更新了”

1. 变更通知按资源区分。高频遥测（心跳、实时速率）走独立的小快照并就地更新对应元素，不触发整页重新读取。
2. 同一时刻的多个变更合并为一次刷新；一次刷新读取多个来源时，只有至少一个来源的内容变化才重画。
3. 断线时回退到较慢的定时读取，并在重连或游标失效后重新读取当前快照。

## 4. 渲染：增量而不是重建

1. 列表按稳定 ID 复用已渲染的行：行的内容和外部依赖（主题、选择状态、紧凑模式等）都没变时直接复用节点，只新建或替换变化的行。加载更多只追加。
2. 返回列表、关闭详情时只更新受影响的行，不整页重读重画。
3. 用户正在输入、选择文本、触摸或滚动时推迟整页重画，交互停止后再应用；任何重画都保留滚动位置、焦点、展开状态和正在阅读的对象。
4. 解析和整理大响应放在主线程之外或分批进行；可见区域外的大量行考虑虚拟化，只在行数确实造成卡顿时引入。

## 5. 静态资源：可缓存的形态

内联在 HTML 里的大段脚本和样式每次打开都要重新传输、解析，浏览器也难以复用已编译代码。超过数 KB 的块改为以内容哈希命名的外部文件，按原顺序同步加载以保持执行语义，`Cache-Control: private, max-age=31536000, immutable`（登录页面的资源仍需鉴权）；CSP 相应允许 `'self'`。拆分前后在同一预览里核对每个页面的元素数量、控制台与网络错误一致。

## 6. 后端代理到下游

前端后端之间还有一跳内部服务时：复用到下游的 HTTPS 连接（设置空闲上限和时长，短于下游的空闲关闭时间）；复用连接被下游关闭时，只对幂等读请求在新连接上重发一次，写请求始终使用新连接，避免重复提交。下游改为 HTTP/1.1 长连接时，每个答复必须带长度或明确关闭；未读完请求体就拒绝的答复要关闭连接，避免残留数据被当作下一请求。

## 验收证据

- 改动前后同一方法的测量记录：网络、回环、体积、浏览器时间及刷新触发频率。
- 304、紧凑格式还原、批量读取无副作用、连接复用与关闭后重发的定向测试。
- 真实浏览器：刷新、加载更多、返回列表时滚动位置和输入保持；拆分资源后各页面无新增控制台或网络错误。
- 新旧客户端与新旧服务端交叉兼容；不能在真机或线上实测的部分写明未验收。
