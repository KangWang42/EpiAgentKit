## 性能

以真实用户 Core Web Vitals 的第 75 百分位为目标：LCP 不高于 2.5 秒、INP 不高于 200 毫秒、CLS 不高于 0.1。开发环境和 Lighthouse 是诊断工具，不冒充线上字段数据。

1. 让主内容和 LCP 资源在初始 HTML 可发现。不要懒加载 LCP 图；仅对确有必要的少数关键资源使用高优先级。
2. 为图片声明 `width`/`height` 或稳定 `aspect-ratio`，使用与显示尺寸匹配的 `srcset`/`sizes`，优先 AVIF/WebP 并保留合适回退。首屏外资源使用原生懒加载。
3. 缩小客户端 JavaScript，删除未使用依赖，按路由或交互边界拆分；公开内容优先静态或服务端渲染。避免用 JavaScript 重现原生 HTML/CSS 已能完成的行为。
4. 字体使用 WOFF2、必要字重和字符子集，设置可靠回退与 `font-display`。只有首屏确定使用的关键字体才预加载。
5. 对稳定资源使用内容哈希和长期缓存；HTML 与动态数据使用符合更新频率的策略。压缩文本资源，避免把大图、完整字体或重复库塞入首屏。

## 技术 SEO 与页面边界

先分类页面：公开且应索引、公开但不应索引、需要登录、后台或临时预览。公开页与后台页分别验收，不把同一套 SEO 要求机械应用到两者。

- 每个可索引页面使用准确且独立的 title、meta description、canonical、语言和一个主 H1；正文层级与标题含义一致。
- 让重要内容以文本存在于 DOM，使用语义 HTML 和真实 `<a href>` 链接。单页应用的独立内容或状态需要稳定 URL。
- sitemap 只包含规范、公开、成功响应页面；lastmod 来自真实内容变化。robots.txt 管抓取，不代替 `noindex` 或登录保护。
- 结构化数据只声明页面真实提供且搜索引擎支持的类型；验证 JSON-LD 与页面可见内容一致，不虚构评分、作者、价格或组织信息。
- 登录、账户、管理、搜索结果、预览和私密页面按产品边界使用 `noindex` 或鉴权，不放入 sitemap。
- 发布后核验实际抓取版本，并监控 4xx、5xx、重定向链、重复标题与 canonical 冲突。

## WCAG 2.2 AA

- 保证键盘可完成核心任务，焦点顺序符合视觉顺序，焦点样式可见且不被固定头部、浮层或 cookie 条遮挡。
- 使用原生 button、a、input、select、textarea 和 dialog；自定义控件必须补齐名称、角色、状态、键盘和焦点管理。
- 每个表单控件有持久可见标签；错误与控件关联，动态状态通过适当的 `aria-live` 告知，不只改变颜色。
- 普通文字对比度至少 4.5:1，大号文字至少 3:1；非文字控件、焦点和传达状态的图形按适用要求至少 3:1。允许浏览器缩放和文本重排，不设置 `user-scalable=no`。
- 关键配色记录实际前景色、背景色、对比度和阈值。半透明、渐变、背景图、混合模式和 hover/focus 等状态应在实际最不利背景上检查；自动工具跳过或近似计算的组合不能直接判为合格。
- 交互目标满足 WCAG 2.2 的最小目标尺寸或间距例外；移动端优先使用更宽裕的触控面积。
- 图片根据功能提供准确 alt；装饰图使用空 alt。视频有字幕或等价内容，图表有文字摘要或数据表。
- 支持 `prefers-reduced-motion`，避免闪烁、自动播放和无法暂停的连续动画。

## 先选验证层级

先根据实际改动和使用该规则、组件或资源的页面选择最小有效证据，不按“网页任务”统一运行全部检查。项目级 `CLAUDE.md`、发布流程或合规要求明确规定的命令优先，通用快速路径不能覆盖它们。

| 层级 | 适用改动 | 最小有效证据 | 默认不做 |
| --- | --- | --- | --- |
| L 局部纯前端 | 文案、颜色、间距、局部 CSS、局部语义标记或既有 DOM 行为；不改变路由、共享布局/组件、依赖、构建配置、API、schema、鉴权、权限、持久化和安全边界 | 目标文件的定向语法/格式检查；HTML 结构或元数据变化时才做目标页静态审计；一个受影响 URL、状态和最危险视口的技术核对；执行者视觉核对或用户对实际页面的明确确认 | 无关全仓测试、整站静态审计、桌面/手机截图矩阵、前后台全状态遍历、生产写探针 |
| P 页面或前端系统 | 新页面、整页改版、共享 token/布局/组件、新交互、路由、依赖或构建行为 | 受影响包的格式化、类型、lint、测试与必要构建；代表性页面、状态、桌面和手机视口；完整技术与视觉门禁 | 未使用本次改动的其它包、页面和状态 |
| P/R 契约或生产高风险 | API、schema、鉴权、权限、持久化、迁移、安全、并发写入或生产配置变化时按 P；用户明确正式发布时按 R | 前端系统证据，加项目规定的隔离测试、拒绝路径和安全检查；R 再加部署检查、只读或安全生产冒烟与健康状态 | 以用户视觉确认替代安全、数据完整性、鉴权或服务健康检查 |

L 任务中，共享选择器或局部组件只扩大到实际使用它的页面；只有修改共享 token、页面外壳、路由或组件契约时才升级到 P。用户明确接手实际页面的视觉验收时，记录 URL、状态、视口或设备以及用户确认的具体角色；该确认只替代本轮局部视觉截图，不替代语法、结构、运行时或健康检查，也不能证明其它页面和状态通过。

部署后的 L 任务只做只读健康检查。用户正在生产页面编辑共享数据时，不运行会写入、回放旧负载或改变 revision 的探针；确需验证写入契约时转入 P/R 高风险路径，使用隔离环境或项目认可的 revision/ETag、幂等和回滚保护。

已知范围外失败只能去重，不能改写为成功。第一次完整记录命令、唯一失败项、原因、范围归属和当前状态；后续 L 修改仅在项目规则允许、相关文件未变化且定向检查没有新异常时不重复运行。未知失败、失败内容变化、健康下降、安全或数据完整性异常必须重新完整定位。

## 共享组件状态与截图基线

本节只适用于新增/重构共享组件，且项目已经存在 Storybook、组件夹具、Playwright 或同等截图回归设施的场景；不得为了单次局部样式修改安装、初始化或接入新平台。

1. 用现有 story/fixture 固化业务中真实存在的默认、长内容、加载、空、错、权限、禁用、窄宽、暗色和减少动效状态；只选择适用项，不虚构产品能力。
2. 行为测试验证点击、键盘、焦点、表单错误和恢复；视觉截图验证布局、颜色、尺寸、裁切和状态外观。DOM 快照、组件截图和实际页面分别回答不同问题，不能互相替代。
3. 固定浏览器及版本、操作系统或容器、字体、视口、设备像素比、语言、时区、测试数据、网络结果和动画策略。环境变化需要重新说明基线适用性，不能把平台差异直接算作产品回归。
4. 第一份基线必须由责任人按组件合同确认。后续失败保留期望图、实际图和差异图；只有确认变化有意且实际使用该组件的代表页面已检查后才更新基线，禁止在测试失败时自动接受全部新截图。
5. 组件隔离门禁通过后仍在代表性实际页面检查容器、路由、数据、鉴权、层级、响应式和与相邻组件的组合关系。

## 浏览器验收矩阵

本矩阵适用于 P 页面/前端系统和 P/R 契约或生产高风险任务；L 局部任务按上一节选择一个受影响场景。先从页面合同选代表场景，至少包含：

- 所有主要公开页面；
- 登录页和至少一个后台列表、详情或编辑页；
- 首屏与至少一个锚点、滚动深处或任务中间状态；
- 真实长标题、长正文、筛选/表单、空、错、加载、成功、弹窗和权限状态中适用的项目；
- 约 1440 像素桌面布局视口与 390 像素手机布局视口；已有暗色模式时增加对应组合。

页面较多时可以按共享模板和组件抽样，但每个独立布局、鉴权边界和高风险交互至少有一个代表页面。单张首页截图不能覆盖整站。

## 真实手机视口

浏览器外窗宽度不等于页面布局视口。Windows Chrome 使用 `--window-size=390` 时，外窗或无头窗口可能仍被钳到更宽的布局视口，再把画面裁成 390 像素；这会制造假溢出，也会漏掉只在真正窄屏触发的断点。

1. 使用 CDP `Emulation.setDeviceMetricsOverride`、浏览器自动化的设备上下文或真实设备，把布局视口明确设为目标宽度。
2. 每个场景记录 `window.innerWidth`、`document.documentElement.clientWidth`、`document.documentElement.scrollWidth` 和 `document.body.scrollWidth`。
3. 手机仿真中只有 `innerWidth` 与 `clientWidth` 接近目标值时，截图才可作为该移动端宽度证据；超过 1 像素的差异先解释设备缩放或错误仿真。桌面 `clientWidth` 可以因垂直滚动条比 `innerWidth` 小，需记录差值并结合溢出判断，不把正常滚动条报成横向布局失败。
4. 横向溢出使用 `max(documentElement.scrollWidth, body.scrollWidth) > clientWidth + 1` 判断，并同时人工检查祖先 `overflow: hidden` 造成的标题、导航、阴影或控件裁切。
5. 记录 `devicePixelRatio`、URL、页面状态和截图文件，使机器报告与图片能够对应。

随附 `audit_browser.py` 使用现有 Chromium 和 CDP 设置布局视口；找不到兼容浏览器时明确报告，不能自行安装，也不能退回外窗窄截图后声称等价。

## 移动端布局与视觉平衡

新页面、整页改版或用户点名手机体验时，在 320、390 和 430 像素附近检查关键页面；390 像素作为统一正式证据，另外两个宽度用于暴露断点边缘、长内容和宽屏手机上的失衡。局部修复只覆盖受影响宽度、共享父容器和同类组件，不扩大为全站重做。

1. 从页面外框开始，依次检查 `page shell`、章节、内容列和主要组件的边界。记录元素矩形、左/右间隙、中心偏移、宽度、逻辑方向的 margin/padding、定位、变换和横向 overflow；先修最早出现共同偏移的父层。
2. 区分内容框与内部文字。正文左对齐、首行缩进或列表标记不等于内容框偏左；判断对象是区块边界、共享对齐线、左右安全区和相邻内容的视觉重量。
3. 居中内容框的左右间隙应与合同一致；全宽媒体、横向滚动区、贴边导航和有意非对称构图按声明的边界验收。非对称区块必须有内容依据、可追踪网格和手机重排，不能用“设计感”解释桌面固定偏移或单边空白。
4. 检查父子两层重复页面边距、固定像素宽度、`min-width`、绝对定位、单边 margin/padding、负边距、`translateX`、跨列和祖先 `overflow: hidden`。没有横向滚动仍可能因裁切或单边偏移失败。
5. 使用真实最长标题、正文、按钮、标签、错误和空状态。分别查看首屏、深层内容和关键任务状态；单个居中英雄区不能证明后续章节、表单、卡片组和页脚也平衡。
6. 浏览器报告的布局几何只提供定位证据，不生成审美分数。未声明且无内容依据的左右间隙明显失衡、多区块共同偏向一侧或核心内容越界时，人工视觉门禁必须判为失败并回到共享布局源修复。

## 每个场景的统一证据

机器报告至少包含：

- URL、标题、布局视口、滚动宽度和横向溢出；
- 页面外框、主要语义区块及其直接内容容器的布局几何，包括左右间隙、中心偏移、盒模型、定位与变换；
- 越出视口的标题、正文、链接、表单、表格与媒体候选，供人工区分真实裁切和有意的横向浏览；
- H1 数量、重复 ID、缺失 alt 和破图；
- 控制台 error、未捕获脚本异常、HTTP 400 及以上响应和网络加载失败；
- 截图路径与截图时的滚动位置；
- 自动检查未覆盖或不能可靠判断的项目。

截图逐屏检查层级、对齐、折行、密度、视觉重心、字体回退、图片裁切、固定元素遮挡和安全区。深层截图应来自 URL 锚点、查询状态或可复现的交互步骤，不用手工拖到大致位置后只保存图片。

## 独立的人工视觉门禁

机器报告只判断可确定的结构、视口、资源和运行时问题。对任何新页面、整体美化或主题重构，使用与机器报告相同 URL、状态和视口的桌面/手机截图，另行记录以下结论：

| 检查项 | 通过条件 | 失败信号 |
| --- | --- | --- |
| 主题与内容 | 构图、字体、材料、配色和组件密度能说明当前内容与读者 | 隐去站名即可原样换给任意产品 |
| 正向/反向合同 | 必须特征可见，禁止项未命中，表达强度符合用户最后要求 | 只实现形容词，没有可定位证据 |
| 视觉重心 | 首屏和关键任务状态各有一个清楚主次 | 多个大标题、深色块、亮色卡或动画同时争夺 |
| 表面层级 | 页面底、嵌套层、浮层与控件关系可追踪 | 每个区块不同浅色或无理由深浅交替 |
| 色彩职责 | 明显色相都能归入操作、强调、语义、数据或真实内容 | 语义色装饰化、竞争色相、未分配强调色 |
| 组件与节奏 | 重复组件有比较或任务依据，长内容密度和章节节奏成立 | 机械卡片阵列、过量胶囊、大片无任务空白 |
| 响应式构图 | 手机端重排主次、内容和操作；页面外框、章节和主要组件的安全区与对齐线符合合同，主题识别仍成立 | 桌面舞台缩小、未声明的单边偏移或空白、父子边距叠加、裁切或隐藏核心内容 |

每项记录“通过、失败、未检查”和一条可定位证据。任一合同禁止项、主题不匹配、主任务被视觉削弱或移动端失去等价路径时，视觉门禁失败。不得把机器报告的 `issues=0`、对比度通过或模型给出的审美分数写成视觉通过；本流程不生成自动审美评分。

视觉门禁不要求所有页面风格相同。营销、正文、账户和管理台可以有不同密度与表达强度，只要共享品牌角色、行为含义和页面合同。

L 局部任务只比较受影响的页面、组件、状态、视口和不变范围，不填写整张全站视觉表。用户已在实际页面确认观感时，把其确认与自动技术检查分别记录；不再为同一局部改动默认补做多组截图，也不把用户确认外推为未查看页面、状态或视口的视觉通过。

## 键盘、触控与状态

1. 用键盘完成核心任务，检查跳过链接、焦点顺序、可见焦点、Escape 关闭、焦点返回、表单错误和浏览器后退。
2. 检查 hover 之外的信息可发现性。触控设备不模拟 hover，重要内容改为常显、点按或展开。
3. 检查软键盘、滚动锁、固定头部、表格、代码块、对话框和浮层。状态变化不能只靠颜色。
4. 在减少动效下重新走核心路径；动效关闭后内容顺序、可见性和操作结果保持不变。

## 候选审阅与部署状态

- `待审阅`：用户正在查看截图、实时页面或明确要求先看候选；允许继续本地或脱敏预览，不进入生产部署。
- `被否定`：当前候选命中用户尚未关闭的整体或局部视觉异议；记录保留项、禁止项和受影响角色，修正后仍回到待审阅。
- `可部署`：用户明确接受当前候选，或用户未进入候选审阅态且内容/任务、技术与视觉门禁均通过。

一次明确局部反馈直接修正受影响角色。同一页面连续两次出现整体风格或配色否定时，停止逐色、逐卡片补丁，重建视觉合同和角色后再产出候选。紧急故障恢复或用户明确要求立即部署时按用户指示执行，并记录未完成的视觉检查。


HTML 结构、元数据或静态构建产物发生变化时，对受影响文件或构建目录运行脚本；纯 CSS、纯文案资源或未改变 HTML 输出的组件样式修改不自动触发整站审计。脚本检查 HTML 语言、viewport、title、description、canonical、H1、main、图片 alt 与尺寸、表单标签、重复 id、阻塞脚本、明显的 LCP 优先级冲突和本地资源存在性。动态路由、实际布局视口、视觉层级、真实对比度、控制台、网络、Core Web Vitals、结构化数据语义和业务流程仍需其它工具或人工检查。
