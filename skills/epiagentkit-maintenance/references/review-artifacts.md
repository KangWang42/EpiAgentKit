# 维护成果审阅

仅新建 skill 或用户明确要求成果审阅时，在制作前读取。日常修复不加载本文件。

新建一个 skill 时，必须在提交前形成至少两份可独立打开、分别验收的真实成果，保存到本次 workbench 的 `review/`。修改、修复、重命名或删除既有 skill 时，默认使用代表性实跑和回归测试验收，不生成审阅成果；只有用户当轮明确要求时才生成，数量与格式服从用户要求，未指定数量时使用两份。成果用于证明 skill 对不同任务输入确实可用，不是把规则文本换一种说法。

#### 目标质量优先

启用成果审阅时，验收标准由用户原始目标和目标 skill 的正式交付约束决定，不能为了缩短工作量退化成最小 smoke test。用户提出“完整、正式、可存档、可提交、与范本同等质量”时，必须先把这些词转成可检查的内容、证据、版式、文件格式和深度要求，再按该标准制作成果；章节标题命中、短提纲、占位表、单页预览、验证日志或“文件能打开”都不能替代目标质量证明。

报告、论文、表单和其他文档型 skill 的审阅成果必须使用用户要求的最终文件格式。用户要求 Word 或学院归档时，成果必须是可打开、可编辑并经过版式检查的 `.docx`；Markdown、纯文本或截图只能作为辅助证据，不能作为唯一报告成果。完整报告的两个输入必须有实质差异，并且各自覆盖目标蓝图中的全部适用模块、表图/附件和设计分支；不得用换标题、缩短内容或同一模板的轻微改写凑数。

如果真实模板、研究事实、引文或其他输入尚未提供，文档型 skill 可以使用明确标注的结构测试模板验证完整模块、篇幅、设计分支和文件流程。先按目标成品或范本为各部分分配不同的深度与篇幅预算；每节写一句说明该节实际功能的示例开头，再用显式测试标记和与该节预算相符的受控填充符检验分页与长文装配，不能把所有章节机械设成同一长度。引文位置只写待核验标记，不能虚构作者、题名、期刊、DOI、研究发现或项目事实。测试模式必须允许这些显式占位并检查结构完整，正式交付模式必须阻断同一文件；索引写明测试成果不能证明真实证据、模板适配或正式归档。缺少关键信息时，应交付待核验/待适配状态并列出阻断项，不能用猜测补全后声称达到正式质量。

长论文、长报告、完整教材或其他一次难以稳定完成的产物，可以分块制作，但必须先建立逐节 todo 或内容矩阵，记录每一部分的功能、唯一输入、证据、依赖、目标格式、完成状态和验收结果。按依赖顺序逐块完成并单独检查，再装配为一个当前版，统一核对术语、数字、引文、编号、表图、交叉引用、目录和分页。分块是保证质量的执行方式，不能把局部草稿、未关闭 todo 或多份碎片文件包装成完整成果；只有所有适用部分关闭并通过整体检查，才计入成果审阅。

成果审阅只属于新建 skill 或用户明确要求的维护任务，不写入目标 skill 的日常业务流程，也不改变目标 skill 每次正常运行的成果数量、任务范围或交付方式。

1. 为目标 skill 选择有实质差异的代表性任务；新建 skill 或用户未指定数量时使用两个，至少一个覆盖新场景，另一个覆盖旧场景或合法边界。
2. 使用新增或修改后的 skill 实际执行任务，并保存直接可检查的结果。根据 skill 类型选择图片、渲染截图、文档、表格、报告、代码产物、命令输出或其它真实文件；问答或审查 skill 保存完整回答或审查报告，脚本或 hook 保存允许与阻止等不同路径的运行结果。
3. 每份成果都必须先通过各自内容流程和文件检查。换色、换标题、轻微排版、格式转换、同一结果的修订前后版、同一日志的拆分或一份失败稿加一份合格稿均不能充当不同代表性任务。验证日志、validator 成功和测试通过只能作为证据，不能替代真实成果。
4. 在 `review/INDEX.md` 写明每份成果的任务输入、独立要求、对应文件、验收结论、覆盖的新旧行为和已知限制；不把用户提供的学习材料、私密数据或项目专属内容复制进通用 skill。
5. 向用户提供 `review/INDEX.md` 和成果的可打开路径后停止在提交前。只有用户明确确认当前成果无误并同意提交，才调用 Git；用户要求修改时重做受影响成果并再次等待确认，旧确认不沿用到新版本。

同一次维护新建多个 skill 时，每个新 skill 都满足以上门槛；既有 skill 只在用户点名要求时生成成果，仅被同步调整的调用者、测试或索引不另算一个目标 skill。成果保留在 workbench 供审阅，不写入 skill 目录，不作为安装负载。
