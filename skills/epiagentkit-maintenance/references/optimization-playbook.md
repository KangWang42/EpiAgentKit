# 库、Skills 与工作流优化手册

仅在进行整库优化、定期精简、上下文减负、评测驱动调优或吸收外部项目与官方实践时读取。日常单点修复不加载本文件。

本手册把维护动作组织为“信号采集 -> 分层定因 -> 最小改写或脚本化 -> 对照评测 -> 同步与记点”的持续改进循环，避免只加不删导致的规则堆积与上下文稀释。

## 1. 先采集真实信号，再决定改什么

每次系统性优化前，用低成本确定性工具获取客观基线，不靠印象拍脑袋改库：

1. **跨端增量反馈**：运行 `python scripts/epiagentkit.py history summary --since-last` 与 `history feedback --since-last`（或按领域定向 `history search`），汇总自上次检查点以来反复出现的纠偏、停顿和偏好。
2. **现场复盘交接**：如有项目生成的 `workflow.txt`，按 `epiagentkit-maintenance` 主流程合并同源根因。
3. **上下文预算体检**：运行 `python scripts/audit_skill_contracts.py --budget`，查看根 `CLAUDE.md` 字符/字节量、全部公开 skill 的 `description` 列表总预算、各 `SKILL.md` 的实际字节体积（重点关注超过 16 KB 的重正文 skill）以及未被直接引用的参考文档。

只针对可复现的高频摩擦或已超预算的热点动手；无真实缺口时保持原样。

## 2. 触发层与执行层分离诊断

一个 skill 没起作用或表现变差，通常分属两类不同根因，对应完全不同的修改动作：

| 现象 | 归属层 | 正确做法 | 禁止做法 |
| --- | --- | --- | --- |
| 该调用时未调用，或无关任务频繁误调用 | 触发层（Layer 1 元数据） | 只改 `description`（能力、用户真实意图词、防止相邻混淆的排除边界）并在 `scripts/skill_routing_cases.json` 补正反例 | 往 `SKILL.md` 正文堆砌长解释或重复写“务必调用本技能” |
| 已加载 skill，但仍漏步骤、越界或输出冗长 | 执行层（Layer 2/3 正文与工具） | 按下方三步排查根因后再做最小改动 | 直接在末尾追加同义警告或泛化禁词表 |

执行层失效按以下顺序排查（优先减法与脚本化，最后才加文字）：

1. **先查上下文稀释（Context Rot）**：中文段落密度高，100 多行 `SKILL.md` 往往已达 20–30 KB，每次激活都占据大量注意力窗口。若关键规则已被淹没在长段落或罕见例外里，优先把条件分支、模板和长清单迁入 `references/`，在 `SKILL.md` 仅留分流条件与清晰链接，并删除重复与防备性铺陈。
2. **再查确定性步骤是否错留在提示词里**：凡是文件解析、结构校验、增量索引、脱敏过滤、链接检查、原始数据防改等机械规则，迁入 `scripts/` 或 `hooks/` 由代码稳定执行，不靠提示词反复叮嘱。
3. **最后补最小决策与停止条件**：确认既非过胖也无法脚本化时，才在最早决策点写入简洁、可验证的判断条件与停止标准，并在同一次修改中删除被取代的旧表述。

## 3. 上下文预算与定期减脂 / 退场

指令预算属于稀缺资源。实证评测表明，冗长或重复的上下文文件会提高推理开销并降低任务通过率，因此优化必须包含主动减法：

- **三层预算基线**：
  - 根 `CLAUDE.md`：保持不超过 200 行且 `<= 12,000` 字符（Antigravity 自动拆分的单规则文件 `<= 24,000` 字节），只留所有会话必知的跨任务边界与总分流；条件细节下沉到对应 skill。
  - 全库 `description` 列表：所有公开 skill 描述总量保持紧凑（远低于客户端约 8,000 字符 / 1–2% 列表预算上限），防止客户端静默截断低优先级技能。
  - 单技能 `SKILL.md`：行数低于 500 只是底线；UTF-8 体积超过 16 KB 时，优先检查是否把条件性参考、长示例或重复免责句留在了正文。
- **定期退场判定（keep / rewrite / merge / move / script / delete）**：
  - 当前主力模型已原生稳定具备的通用教程与常识说明 -> 删除。
  - 已被 `scripts/` 或 `hooks/` 确定性接管的防错提醒 -> 删除正文重复条款，只留脚本调用方式。
  - 仅对应某次旧版本缺陷、已无复现路径的防御性补丁 -> 经旧/新任务核验后删除。
  - 两个 skill 触发边界高度重叠且长期引发误调用 -> 合并或明确主次入口与排除条件。
  - 长时间不被任何流程引用的孤立 `references/` 文件 -> 核实后归档或删除。

## 4. 评测驱动的 A/B 迭代

静态关键词测试只能防止既有条款被误删，不能证明模型行为变好。涉及任务分流、核心工作流或大幅改写时，按“基线 -> 改动 -> 对照 -> 取舍”验证：

1. **构造代表性用例集**：至少包含正例（应触发且应通过的真实任务）、负例（表面相似但应排除的边界任务）与旧例（必须继续成立的回归任务），使用隔离输入与真实文件，不泄漏私密研究数据。
2. **同题对照评测**：用相同输入比较旧版（或无该 skill 的基线）与新版，记录四项指标：任务完成质量与通过率、是否产生未经请求的额外工作、不必要询问或停顿次数、以及可测量的文件体积/工具调用步数变化。
3. **以净收益为合入门槛**：若新版增加了说明体积或工具步数，却未在通过率、准确率或返工率上带来可观察改进，则否决该改动；两版通过同一评测时，优先保留更短、唯一来源更清楚的一版。
4. **独立复核与收口**：高风险或跨多 skill 改动在条件允许时用隔离上下文复核实际产出；提交并通过三端 `sync` 与 `doctor` 后，运行 `python scripts/epiagentkit.py history mark --note "<本次主题>"` 推进检查点，使下一轮优化只关注增量新问题。

## 5. 吸收外部实践与优秀仓库

当用户提供外部仓库、开源 skill、论文或官方更新要求借鉴时，按四步筛选，防止盲目拼接：

1. **核验一手依据**：直接阅读目标仓库源码、官方文档或可复现样例，区分经过验证的机制与营销口号。
2. **映射到既有体系**：先查 `knowledge_index.py` 和 `CLAUDE.md`，确认本仓库是否已有对应唯一维护位置，避免另起炉灶。
3. **独立增量判定**：逐项评估外部做法在现有规则已生效的前提下，是否真的带来独立行为收益（如更好的确定性脚本、更清晰的分流条件或更低上下文开销）；对已经覆盖或会引入额外负担的部分明确舍弃。
4. **适配三端与最小合入**：把确有收益的机制按本仓库唯一来源结构与三端兼容性（Claude Code、Codex、Antigravity）重写融入，保留本仓库原有优势，不照搬外部目录结构、冗长样板或客户端专属字段。
